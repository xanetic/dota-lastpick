## 0. Контекст и философия

**Что есть сейчас.** Игра: показываем 9 героев из про-матча, пользователь угадывает 10-го (last pick).
Под капотом уже лежит рабочий корпус данных:

- `data/matches.json` — ~990 про-матчей (11 Интернешнлов + 20 Мейджоров/LAN, 2014–2026).
  Каждый матч: `picks[]` (hero_id, team, **order**, player), `bans[]` (hero_id, team, order),
  `answer` (последний пик = пик с макс. order), команды, лига, год, исход.
- `data/heroes.json` — 127 героев (primary_attr, картинки).
- Источник: OpenDota API (можно дотянуть до 50–100k матчей и до per-player статистики
  `hero_damage / tower_damage / hero_healing / stuns / teamfight_participation / lane_role`).

**Главный принцип продукта.** Ценность — не «кто кого контрит» и не винрейты,
а **объяснение логики решения через факторы драфта**. Движок отвечает на вопрос
капитана/тренера: *«какую задачу команда закрывала этим пиком и почему именно этот герой».*

**Три запрета (вшиты в дизайн):**
1. ❌ Никаких утверждений вида «X контрит Y» как первичной логики — они ложны вне контекста.
2. ❌ Винрейт героя не является основной ценностью (допустим только как слабый вторичный сигнал со сжатием и дисклеймером).
3. ❌ Не клонируем Dotabuff (агрегатор статов). Мы — reasoning layer поверх статов.

**Северная звезда (north-star метрика инженерного качества):** top-k accuracy предсказания
реального last pick на отложенных про-матчах. Если движок реально «понимает» драфт —
он угадывает, что выбрали профи. Эта же метрика валидирует и игру, и аналитику.

**Ключевое инженерное требование — faithfulness объяснений.** Скоринг строим *аддитивно
и интерпретируемо*, чтобы объяснение выводилось из самих весов модели (декомпозиция вклада),
а не дописывалось пост-фактум LLM-кой как правдоподобная выдумка. Объяснение = разложение
скора, а не отдельная «история».

## 1. Draft Reasoning Engine — архитектура

Движок — это конвейер из слоёв. Вход: множество известных героев (9, или N на любой фазе
драфта) + баны + сторона + контекст (патч, тир, команды). Выход: вектор потребностей,
ранжированные кандидаты, объяснение, архетип.

```
            ┌────────────────────────────────────────────────────────────┐
            │ INPUT: known_picks[], bans[], side, patch, teams (optional)  │
            └────────────────────────────────────────────────────────────┘
                                     │
        ┌────────────────────────────┼─────────────────────────────┐
        ▼                            ▼                              ▼
┌───────────────┐         ┌────────────────────┐        ┌────────────────────┐
│ Hero Attribute│         │  Role / Position    │        │  Meta Layer         │
│ Graph (§2)    │         │  Solver             │        │  (patch contest /   │
│ a_h ∈ [0,10]^K│         │  (какие позиции 1–5 │        │   presence, §3.MetaFit)
└───────┬───────┘         │   ещё открыты)      │        └─────────┬──────────┘
        │                 └─────────┬──────────┘                   │
        ▼                           │                              │
┌───────────────────────────────────────────────┐                │
│  Need Detection (§1.2)                          │                │
│  C = aggregate(a_h по известным героям)         │                │
│  T = target_profile(archetype, enemy_draft)     │                │
│  R = relu(T − C)   ← незакрытые потребности      │                │
└───────────────────────┬─────────────────────────┘               │
                        │                                          │
                        ▼                                          │
            ┌──────────────────────────┐     ┌────────────────────▼─────────┐
            │  Synergy Graph (§3)       │     │  Historical Draft Intelligence │
            │  S[h, hi] (combo + lift)  │     │  (similar-state retrieval, §5) │
            └─────────────┬─────────────┘     └────────────────┬───────────────┘
                          │                                    │
                          ▼                                    ▼
            ┌──────────────────────────────────────────────────────────┐
            │  Candidate Ranking (§3) — аддитивный скор Score(h | state) │
            └───────────────────────────┬──────────────────────────────┘

            ┌──────────────────────────────────────────────────────────┐
            │  Explanation Generator (§4) — декомпозиция скора в факторы │
```

Параллельно работают офлайн-агрегаты: **Draft DNA (§6)**, **Exploit Report (§7)**,
**Archetype Classifier (§8)** — они потребляют тот же Attribute Graph и историю.

- вражеским драфтом (у врага высокий `mobility` → растёт `pickoff_catch`/`anti_mobility`;
  у врага высокий `splitpush` → растёт `defense_waveclear`);
- патчем (мета-модуляция).

### 1.2 Need Detection — формула

Для известных героев `D` (известная сторона):

1. **Текущее покрытие** по каждой оси `k` — c **убывающей отдачей** (4-й танк бесполезен):
   ```
   C_k = g( Σ_{h∈D} contrib_k(a_h) ),   g(x) = x^γ,  γ ≈ 0.6   (вогнутая, diminishing returns)
   ```
   где `contrib_k` — проекция атрибутов героя на ось `k` (матрица отображения M, §2.3).
2. **Целевой профиль** `T_k` — «здоровый драфт» (бейзлайн, откалиброван по реальным
   победным про-составам), модулированный архетипом и вражеским драфтом.
3. **Остаточная потребность**:  `R_k = relu(T_k − C_k)`, затем нормировка `R̂ = R / Σ R`.

`R̂` — это вектор «чего драфту не хватает». Он напрямую идёт и в ранжирование (§3),
и в объяснение (§4: «команде нужны были …»).

## 2. Hero Attribute Graph — структура данных героя

Роли (carry/support) — слишком грубо. Описываем героя **вектором непрерывных атрибутов**
`a_h ∈ [0,10]^K`. Это и есть «ДНК героя».

### 2.1 Полная схема атрибутов (K ≈ 32), сгруппировано

```jsonc
Hero {
  // --- идентичность ---
  "hero_id": 129, "name": "Mars", "primary_attr": "str",

  // --- бой / файт ---
  "frontline": 0-10,            // насколько может стоять первым/танковать
  "initiation_hard": 0-10,      // форс-инициация (Arena, Blink combo)
  "initiation_soft": 0-10,      // дальняя/позиционная инициация
  "teamfight_aoe": 0-10,        // массовый урон+контроль в замесе
  "teamfight_sustained": 0-10,  // длительный ДПС по площади
  "burst": 0-10,                // взрывной урон по одиночке
  "pickoff_catch": 0-10,        // поймать/добить мобильную цель
```

### 2.2 Как получить значения атрибутов (без ручной разметки всего)

**Гибридный bootstrap → экспертная коррекция:**

1. **Data-derived приоры** из агрегатов OpenDota (per-hero усреднение по тысячам матчей):
   - `tower_pressure` ← avg `tower_damage`/min;
   - `save_peel`, `sustain_heal` ← avg `hero_healing`;
   - `pickoff_catch` / `lockdown_duration` ← avg `stuns` (сумма длительности контроля);
   - `teamfight_*` ← `teamfight_participation` + `hero_damage` в окнах файтов;
   - `splitpush` ← высокий `tower_damage` при низком `teamfight_participation`;
   - `scaling_lategame` ← перформанс/нетворт в матчах 40+ мин (кривая GPM/нетворта по времени);
   - `lane_dominance` ← lane win-rate на стадии лайнинга (parsed-данные).
2. **Metadata-derived** из описаний абилок/талантов (Valve dota2 game data / OpenDota constants):
   - `mobility` (наличие blink/leap), `bkb_pierce` (типы контроля), `dmg_*` (типы урона),
     `flex_positions` (по historical позициям).
3. **LLM-приоры**: модель проставляет недостающие оси по описанию героя (структурированный
   вывод 0–10) — как тёплый старт.
4. **Экспертная коррекция**: аналитик правит спорные значения. 127×32 ≈ 4k чисел —
   делается за пару заходов с приорами.
5. **Версионирование по патчам**: атрибуты привязаны к диапазону патчей; герой может
   меняться (ребаланс) → `hero_attributes(hero_id, patch_window)`.

> Принцип: data-derived приоры объективны, но «зашумлены» текущей метой; экспертная правка
> ловит то, что статы не видят (потенциал, ролевая интерпретация). Поэтому гибрид.

### 2.3 Матрица отображения M (атрибуты → потребности)

Need-оси (§1.1) считаются из атрибутов через разреженную матрицу `M [need × attr]`.
Часто это 1:1 или простая сумма, напр.:
```
need.teamfight_aoe   = 0.7·teamfight_aoe + 0.3·zone_control
need.initiation_hard = initiation_hard
need.pickoff_catch   = 0.6·pickoff_catch + 0.2·burst + 0.2·anti_mobility
```
`M` тоже обучаема, но стартует с экспертных коэффициентов (интерпретируемость).

## 3. Candidate Hero Ranking — математическая модель

После появления известных героев генерируем рейтинг возможных last pick (или next pick
на любой фазе). **Без винрейта как основы.**

### 3.1 Аддитивный скор

```
Score(h | state) =  α · NeedFit(h, state)
                 +  β · Synergy(h, D_self)
                 +  γ · MetaFit(h, patch)
                 +  δ · HistoricalPrior(h | state)        ← из §5
                 +  ε · PositionFeasibility(h, state)
                 −  ζ · Redundancy(h, D_self)
                 −  η · BannedOrTaken(h)
```

Все слагаемые в сопоставимых единицах (z-score / 0–1). Веса `α…η` **обучаются**
(см. §3.6). Аддитивность ⇒ объяснение = разложение Score по слагаемым (faithful, §4).

### 3.2 NeedFit — маржинальное закрытие потребностей (ядро)

Не «сколько у героя статов», а **сколько он добавляет к незакрытому**:
```
NeedFit(h) = Σ_k  R̂_k · [ g(C_k + contrib_k(a_h)) − g(C_k) ]
```
`g` вогнутая (diminishing returns) ⇒ герой, дублирующий уже закрытую ось, получает мало;
герой, закрывающий дефицит `R̂_k`, — много. Это математически кодирует «закрытие
незаполненных потребностей».

### 3.3 Synergy — граф синергий (не «контрпики»)

`S[h, hi]` — сила парной синергии. Два источника, складываются:
1. **Curated combo-rules** (сетап → выплата, стекинг контроля):
   *Magnus RP → AoE-кор*; *Mars Arena → площадной урон*; *Disruptor Static Storm + Phoenix
   Supernova*; *инициатор + follow-up контроль*. Хранится как типизированные правила
   (`provides:setup` ↔ `needs:payoff`), а не хардкод пар.
2. **Co-occurrence lift** из истории (empirical Bayes со сжатием для малых выборок):
   ```
   lift(h,hi) = P(h,hi вместе) / (P(h)·P(hi)),   shrink к 1 при малом n
   ```
   Lift ловит «команды реально берут их вместе», но БЕЗ заявления о причинности —
   в объяснении формулируем как «исторически сочетается с …», не «контрит».
```
Synergy(h, D_self) = Σ_{hi ∈ D_self} S[h, hi]
```

### 3.4 MetaFit — мета без винрейта во главе

```
MetaFit(h) = z( contest_rate(h, patch_window) )         // (pick+ban)/games — присутствие/контест
           + λ · shrink( z(winrate(h)) )                // λ мал; со сжатием; вторичный сигнал
```
Контест-рейт (насколько героя «уважают» — берут или банят) — честный сигнал меты;
винрейт идёт лишь как слабая добавка с дисклеймером.

### 3.5 PositionFeasibility и Redundancy

- **PositionFeasibility**: Role/Position Solver определяет, какие позиции 1–5 ещё открыты
  у команды (по уже взятым героям и их `flex_positions`); кандидат, который не влезает ни
  в одну открытую позицию, штрафуется/отсекается. Это убирает абсурдные кандидаты
  (например, 6-й саппорт).
- **Redundancy**: штраф за дублирование уже закрытой роли/оси сверх меры
  (комплементарно diminishing returns в NeedFit).

### 3.6 Обучение весов и валидация

- **Задача обучения:** на исторических драфтах предсказать фактический следующий/последний
  пик. Learning-to-rank (например, softmax/pairwise) над кандидатами; целевой — реально
  выбранный герой.
- **Метрики:** top-1 / top-3 / top-5 accuracy, MRR, NDCG на отложенных матчах
  (split по времени: учим на старых патчах, тестим на новых — честно к мете).
- **Калибровка вероятностей** (temperature scaling) — чтобы «24%» означало 24%.
- Тот же скоринг = ядро игры (рейтинг кандидатов) и аналитики. Одна модель — две витрины.

## 4. Explanation Generator — структура объяснения

После показа правильного героя строим объяснение **из разложения Score** (faithful).
LLM используется только для «причёсывания» формулировок поверх жёстко заданных фактов
(structured facts → natural language), чтобы исключить выдумку.

### 4.1 Логическая структура

```
1. ПОТРЕБНОСТИ КОМАНДЫ (top-3 по R̂):  что было не закрыто у 9 героев
2. РОЛЕВОЙ/ПОЗИЦИОННЫЙ ПРОБЕЛ:        какая позиция оставалась
3. КАНДИДАТЫ (top-k по Score):        реальные альтернативы
4. ПОЧЕМУ ВЫБРАННЫЙ ВЫШЕ:            разложение его Score по факторам
   - какие потребности закрыл (вклад NeedFit по осям)
   - какие синергии активировал (конкретные партнёры из S[h,hi])
   - мета/позиция
5. ИСТОРИЧЕСКОЕ ПОДКРЕПЛЕНИЕ (§5):    «в N похожих драфтах брали это в X% случаев»
6. УВЕРЕННОСТЬ + ОГОВОРКИ:           confidence, и честно где модель не уверена
```

## 5. Historical Draft Intelligence — поиск похожих драфтов

**Задача:** для текущих 9 (или N) героев найти исторически похожие *состояния драфта*
и посмотреть, что выбирали дальше.

### 5.1 Представление состояния (embedding)

Вариант A (старт, простой): **композиционный фингерпринт** —
`v(state) = Σ_{h∈D} a_h` (сумма атрибутных векторов) ⊕ контекст (сторона, патч-бакет,
фаза/order, баны как negative-mask).
Вариант B (зрелый): **hero2vec** — обучаем эмбеддинги героев skip-gram’ом по последова-
тельностям пиков (как word2vec по «предложениям»-драфтам). Состояние = агрегация
эмбеддингов выбранных героев. Ловит «латентные роли» из реального поведения команд.

### 5.2 Поиск соседей

```
similarity = cosine( v(state), v(state_i) )
фильтры:    патч-окно, тир турнира, та же сторона/фаза, (опц.) исключить ту же серию
вес соседа: w_i = similarity_i · recency_decay(patch_i)
```
ANN-индекс (FAISS / hnswlib) для масштаба 100k+ состояний. Для каждого матча генерируем
несколько «состояний» (после 5, 6, …, 9 пиков) → большой корпус из малого числа матчей.

### 5.3 Эмпирическое распределение

Среди top-N соседей смотрим, какой герой/архетип шёл следующим:
```
P(h | state) = Σ_{i: next_i = h} w_i  /  Σ_i w_i      (взвешенно по похожести и свежести)
```
Это даёт и `HistoricalPrior` для §3, и блок §4.5 («в 700 похожих случаях: Mars 24% …»).
Обязательно показываем `N` (размер выборки) и доверительный интервал — честность важнее
красивой цифры.

## 6. Draft DNA — профилирование команд (ядро ценности для команд)

Профиль команды как набор интерпретируемых метрик 0–10. **Без винрейта в основе** —
по паттернам *выбора и поведения*.

### 6.1 Метрики (как считаются)

Всё считается как **z-score относительно бейзлайна лиги/тира**, затем сжимается в 0–10.
Разделяем **draft-derived** (есть только из пиков — доступно сразу) и **game-derived**
(нужны тайминги/статы матча — позже).

| Метрика | Тип | Как вычисляется (сигналы) |
|---|---|---|
| `Aggression` | draft + game | доля `early_tempo`/инициаторов в составах; (game) ранние тайминги вышек, FB-time, темп нетворта |
| `Greed` | draft + game | частота 2+ `networth_dependence`-коров; средний `scaling_lategame`; (game) farm-приоритет, среднее время игр |
| `Teamfight` | draft | средний `teamfight_aoe`+`initiation_hard` состава |
| `Split Push` | draft + game | средний `splitpush`/`mobility`; (game) распределение урона по строениям по карте |
| `Pickoff` | draft | средний `pickoff_catch`+`burst`+`map_control_vision` |
| `Flexibility` | draft | энтропия пула героев + позиционная гибкость + «как поздно раскрывают» ключевых героев (порядок order) |
| `Comfort/Signature` | draft | герои, выбираемые сильно выше базовой частоты (lift над лигой) |
| `Lane Focus` | game | тренд: трилейн/агро-лайны/сейв-лайны |
| `Adaptability` | draft | дисперсия архетипов (§8) от игры к игре vs зацикленность на одном |
| `Draft Tempo Curve` | draft | агрегированная `power_spike_timeline` состава — когда команда «сильна» |

### 6.2 Построение профиля

```
team_vector = robust_mean_over_matches( per_match_feature_vector )
              (взвешено по свежести; min N матчей, иначе помечаем low-confidence)
profile_score_m = 10 · sigmoid( z(team_vector_m) )
```
Профиль версионируется по составу ростера (смена игроков → новый «период» команды).
Radar-chart как у тебя в примере (Aggression/Greed/Teamfight/Split/Flex).

## 7. Exploit Report — разбор соперника

Для заданной команды — что эксплуатировать. **Через паттерны поведения, не винрейт.**

### 7.1 Содержимое

- **Любимые первые пики** (по стороне/фазе): что открывают, как часто.
- **Любимые ластпики / финишеры драфта.**
- **Любимые архетипы (§8)** и распределение по ним.
- **Сигнатурные герои/связки** (high-lift пары §3.3).
- **Предсказуемость (conditional patterns):**
  `P(hero | уже взяли X)`, `P(архетип | враг забанил Y)`, `P(next | order=k)`.
  Метрика предсказуемости = насколько низка энтропия их следующего пика в типовых
  состояниях (низкая энтропия = легко читать = эксплойт).
- **Слабые места драфта (blind spots):**
  - оси, которые их типовые составы стабильно **недозакрывают** (низкое покрытие
    `highground_defense`/`defense_waveclear` → уязвимы к Deathball/Split);
  - архетипы, которые они почти не умеют играть (нет в репертуаре → выводить их туда);
  - типовая `power_spike_timeline` → когда их состав слаб (тайминг-эксплойт).
- **Ban-suggestions (information-gain):** не «забань самого сильного», а герой/связка,
  бан которой **максимально схлопывает их достижимые архетипы / закрытие потребностей**
  (greedy max-coverage по их вероятностному дереву пиков).

### 7.2 Алгоритм ban-suggestion (эскиз)

```
для каждого кандидата на бан b:
    смоделировать их вероятностное дерево драфта без b (через модель §3 как их «капитана»)
    Δ = (ожид. сила/гибкость их драфта с b) − (без b)
ранжировать b по Δ   →  баны, бьющие по их паттернам, а не по абстрактной силе
```

## 8. Draft Archetypes — система архетипов

### 8.1 Прототипы (вектор в пространстве потребностей §1.1)

Каждый архетип = эталонный профиль (что он максимизирует / минимизирует):

| Архетип | Высокое | Низкое |
|---|---|---|
| **Tempo** | early_tempo, mobility, pickoff | scaling |
| **Teamfight** | teamfight_aoe, initiation_hard, frontline | splitpush |
| **Deathball** | tower_pressure, early_tempo, teamfight_aoe, frontline | scaling, splitpush |
| **Zoo** | summons (anti_summon-устойчивость), tower_pressure, map_control | save_peel |
| **Pickoff** | pickoff_catch, burst, mobility, vision | teamfight_sustained |
| **Protect Carry** | save_peel, scaling_lategame, auras | early_tempo |
| **Split Push** | splitpush, mobility, tower_pressure | teamfight_aoe |
| **High Ground Defense** | defense_waveclear, save_peel, teamfight_aoe, highground_defense | early_tempo |

### 8.2 Классификация драфта

Два подхода, используем оба:
1. **Soft rule-based:** считаем need-coverage вектор состава, косинус к каждому прототипу
   → primary + secondary архетип с confidence. Интерпретируемо, работает с 1-го дня.
2. **Unsupervised discovery:** k-means/GMM над композиционными векторами реальных
   победных составов → кластеры; метим кластеры по доминирующим осям. Сверяем с
   названным списком, при необходимости добавляем найденные «новые» архетипы.
   Это защищает от навязывания теории данным (data-driven архетипы меты).

Драфт обычно гибрид (Teamfight-Deathball) → отдаём распределение, не один лейбл.

**Сложность:** средняя (ETL, эмбеддинги, eval-харнес).
**Ценность:** объяснения подкреплены реальной историей и метой; рейтинг кандидатов измеримо точен.

**Функционал:**

- Draft DNA (§6) — страницы команд, radar, версии по ростеру.
- Exploit Report (§7) + ban-suggestion engine.
- Sequential draft model: предсказание next pick на **любой** фазе (не только last) —
  transformer/последовательностная модель над порядком драфта.
**Сложность:** высокая (data engineering, последовательностное ML, UX дашбордов).
**Ценность:** первый реально полезный инструмент для тренеров — скаут соперника и подготовка к серии.

### Phase 4 — «Продукт для Tier-3 команд» (продуктизация)
**Функционал:**

**Сложность:** высокая (надёжность realtime, доступ к live-данным драфта, инфра).
**Ценность:** B2B-инструмент капитана/тренера; монетизация (подписки команд/орг).

## 10. Тех-стек, данные, риски, валидация

**Стек (предложение):**
- Данные/ETL: Python, OpenDota API, (позже) парсинг реплеев; хранилище — Postgres
  (+ JSONB для драфтов) или DuckDB/Parquet для аналитики; FAISS/hnswlib для ANN.
- Движок: Python-сервис (FastAPI) с аддитивной моделью (L2R на sklearn/NumPy);
  атрибуты/синергии — версионируемые таблицы.
- Фронт: текущий статик-сайт растёт в SPA по мере надобности; объяснения — JSON-контракт §4.3.
- LLM: только для NL-обёртки структурированных фактов (grounding), не для решений.

**Данные (схема, кратко):**
```
heroes(hero_id, name, primary_attr)
hero_attributes(hero_id, patch_window, <32 атрибута>)        -- версионно
matches(match_id, league, tier, patch, start_time, radiant_win, ...)
picks_bans(match_id, hero_id, is_pick, team, order, player)  -- уже есть
draft_states(state_id, match_id, after_order, known_set, side, next_hero)  -- генерируем для §5
team_profiles(team_id, roster_period, <метрики DNA>, n_matches, confidence)
synergy(hero_a, hero_b, curated_score, lift, n)
meta_stats(hero_id, patch_window, contest_rate, winrate, n)
```

**Риски и как смягчаем:**
- *Атрибуты субъективны* → версионирование + data-derived приоры + измеримость через top-k.
- *Мета дрейфует* → патч-окна, recency-decay, переобучение по расписанию.
- *Малые выборки (Tier-3 команды)* → empirical Bayes shrink, явные confidence/low-data флаги.
- *Соблазн скатиться в винрейты/контрпики* → архитектурный запрет: винрейт лишь как
  слабое слагаемое; «контрпик» переформулирован в «закрытие потребности/синергию».
- *Faithfulness объяснений* → аддитивная модель, объяснение = декомпозиция, не пост-рационализация.

**Валидация качества reasoning:**
1. Количественно: top-1/3/5 accuracy и MRR предсказания реального пика (time-split).
2. Калибровка: reliability diagram по вероятностям из §5/§3.
3. Экспертная оценка объяснений: слепой рейтинг аналитиками (полезно/верно/банально),
   сравнение с baseline «просто винрейт» — должны выигрывать по «инсайтности».
4. (Phase 4) A/B: помогает ли подсказка капитанам (прокси — субъективная оценка + later
   качество драфта по нашим же метрикам).
